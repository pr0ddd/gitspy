## 1. Где мы сейчас

Построено за первый заход — вертикальный срез вместо этапов из спеки: ядро → чтение → Tauri → отрисовка.

| Слой | Состояние |
|---|---|

| `gitspy-repo` | Чтение через `gix`: обход, метаданные, refs. **Тестов нет** |
| `src-tauri` | Три команды: `open_repo`, `commit_range`, `current_path` |
| Фронтенд | Вся строка на canvas, свой скролл, мини-карта, аватарки-идентиконы. **Тестов нет** |

## 2. Долги

### Блокирующее

**Порядок обхода нарушает топологию.** `gix` с сортировкой `ByCommitTime` не гарантирует, что родитель идёт после потомка — в отличие от `git log --date-order`, где на react таких нарушений **ноль**. Наш код в `gitspy-repo/src/lib.rs` молча считает такого родителя «внешним» и открывает дорожку, которая никогда не закрывается. Результат: 191 фантомная линия и **219 дорожек вместо примерно двадцати**.

Это не косметика. Граф на большом репозитории показывает структуру, которой в истории нет, и вся работа над отрисовкой поверх этого бессмысленна.

**У слоя чтения нет ни одного теста.** Инверсия: чистое и детерминированное ядро покрыто 53 тестами, а слой, который трогает реальный мир и содержит блокирующий дефект, не покрыт ничем. Спека (раздел 8) предписывает дифференциальные тесты против настоящего git — их нет.

### Существенное

**Все метаданные грузятся в память фронтенда при открытии.** 12.3 МБ текста на react проходят через IPC и оседают в JS-массивах.

**Контракт IPC написан руками дважды** — структуры в `src-tauri/src/main.rs` и их копия в `src/types.ts`. Спека требовала генерации из Rust. Это тот самый дефект старого приложения, ради ухода от которого всё затевалось: там контракт был написан руками трижды.

**Отрисовка непроверяема.** `render.ts` — 602 строки, одна функция рисует восемь слоёв. Тестов нет, и единственный способ проверить визуальное изменение — показать пользователю скриншот. Последние три десятка правок так и шли: скриншот → догадка → мимо → повтор. Это дорого и не масштабируется.

**Палитра 12 цветов против 219 дорожек.** После починки порядка обхода дорожек станет ~20, но запас всё равно нужен.

### Отложенное сознательно

Свёртка цепочек и подсветка предков были сделаны и удалены. Выделение текста мышью потеряно вместе с переходом на canvas. Операционного слоя (`gitspy-exec`) не существует.

## 3. Слой данных и загрузок

Проектируется целиком сейчас, потому что дальше в него ложатся файлы коммита, diff, blame, аватарки с GitHub, статусы PR и проверок — и каждое из этого имеет разную цену и разную политику загрузки. Прикручивать их по одному значит получить четыре несогласованных механизма кэша.

### Четыре рода данных

| Род | Примеры | Цена | Политика |
|---|---|---|---|
| **Каркас** | топология, refs | 19 мс на 35k | Читается целиком при открытии, **блокирует показ** |
| **Оконные** | сообщения, авторы, даты | микросекунды на окно | Диапазонный кэш с LRU, запрос при смене окна, отмена устаревших |
| **Точечные** | файлы коммита, ханки diff, blame | десятки мс | Кэш по ключу, отмена при смене выбора |
| **Внешние** | аватарки, статус PR, CI, ревьюеры | сетевой запрос, лимит API | **Никогда не блокируют**, кэш на диске с TTL, дедупликация, backoff |

### Правило, определяющее политику

**Блокируем на том, что меняет геометрию. Не блокируем на том, что меняет только пиксели.**

Топология определяет, где что находится — без неё рисовать нечего, ждём. Аватарка не меняет ни одной координаты: кружок уже нарисован в правильном месте, картинка втекает в него позже. Статус проверок — тем более.

Это же правило запрещает повторить главный дефект старого приложения, где открытие репозитория блокировалось на походе в GitHub API за аватарками, то есть ждало **сеть** ради косметики.

### Где кэш на диске нужен, а где нет

**Не нужен для раскладки.** Она стоит 19 мс, а сам репозиторий уже лежит на диске: база объектов git — это и есть кэш, сжатый, проиндексированный и всегда согласованный с историей. Свой файл поверх неё дублирует данные и заводит класс тихих багов с устаревшей инвалидацией, который спека сама называет самым опасным.

**Нужен для внешних данных.** У них локального источника нет вообще. Аватарка стоит сетевого запроса и расхода лимита API; при перезапуске приложения без кэша всё качается заново. Ключ — почта автора или идентификатор объекта, а не путь репозитория: аватарки общие для всех репозиториев.

### Инвалидация

Два независимых контура, и смешивать их нельзя:

- **Локальные данные** — от изменения refs и от наблюдателя за файловой системой, через единую точку. Один путь и для операций, выполненных нами, и для сделанных в терминале мимо нас.
- **Внешние данные** — по TTL и по явному обновлению. Смена HEAD не делает аватарку устаревшей.

### Общие требования ко всем родам

Дедупликация одновременных запросов одного ключа. Отмена при уходе окна или смене выбора. Отсутствие данных — **нормальное состояние отрисовки**, а не ошибка: строка без метаданных рисуется прочерком, узел без аватарки — цветным кружком.

## 4. Фазы

Порядок продиктован одним правилом: **сначала то, без чего всё построенное выше врёт или не масштабируется.**

### Фаза 1. Правильное чтение

**Зачем.** Граф на большом репозитории показывает структуру, которой нет.

**Что входит:**
- Разделить чтение на два прохода. Первый — топология: `oid` и родители из `info.parent_ids`, без `find_object` и `decode`. Второй — метаданные, только по запросу окна.
- Своя сортировка вместо доверия к `gix`: алгоритм Кана с приоритетной очередью по времени коммита — ровно семантика `git log --date-order`, гарантирующая, что родитель идёт после потомка. На 35 тысячах единицы миллисекунд.
- `outside_parents` остаётся только для честно обрезанного окна, а не как затычка под нарушение порядка.
- Дифференциальные тесты против настоящего git: порядок против `git log --all --date-order`, refs против `git for-each-ref`.
- Краевые случаи: пустой репозиторий, bare, detached HEAD, аннотированные теги, shallow-клон.

**Готовность:** на react `outside_parents == 0`, дорожек около двадцати, время до готовой раскладки менее 50 мс, дифференциальные тесты зелёные.

---

### Фаза 2. Слой данных и загрузок

**Зачем.** Дальше в него ложится всё: файлы коммита, diff, интеграции. Спроектировать один раз дешевле, чем сводить четыре механизма потом.

**Что входит:**
- Четыре рода данных из раздела 3 как явные понятия в коде, а не как соглашение.
- `HistorySource` — оконные данные: кэш по диапазонам с LRU и склейкой соседних.
- Точечные ресурсы — кэш по ключу с отменой. Первый потребитель: **список файлов коммита по клику**.
- Каркас внешних ресурсов: дисковый кэш с TTL, дедупликация, backoff. Первый потребитель — аватарки; пока локальные идентиконы, но через тот же путь.
- Единая точка инвалидации локальных данных.

**Готовность:** открытие react показывает граф быстрее чем за 100 мс; память renderer ограничена и не растёт со скроллом; клик по коммиту показывает его файлы; быстрый скролл не спотыкается об IPC.

---

### Фаза 3. Контракт и проверяемость отрисовки

**Зачем.** Без этого каждая следующая фаза добавляет ручной работы и тихих расхождений.

**Что входит:**
- Генерация типов TypeScript из Rust: рассинхрон становится ошибкой сборки.
- Разрез отрисовки надвое: чистая функция «геометрия + окно → список примитивов» и тонкий слой, кладущий примитивы на canvas. Единая `GraphGeometry` сохраняется — она и есть вход чистой функции.
- Тесты: виртуализатор, `HistorySource`, примитивы отрисовки. Canvas попиксельно не тестируется.
- Возврат подсветки предков и потомков — уже на нормальном слое состояния.
- Выделение текста: DOM-подложка под строкой курсора, не ломающая скролл.
- CI: сборка, тесты, clippy, бенчмарк раскладки с порогом.

**Готовность:** визуальное правило можно изменить и увидеть в тесте, что сломалось. Правки перестают требовать скриншота на каждый шаг.

---

### Фаза 4. Diff

Ханки через `imara-diff` — ту же библиотеку, что gitoxide использует внутри. Панель просмотра изменений, сравнение по строкам и по словам.

Список файлов коммита уже есть с фазы 2 — здесь добавляется содержимое.

**Готовность:** сравнение с `git show` сходится на тестовых репозиториях.

---

### Фаза 5. Интеграции

GitHub первым, остальные по той же схеме. Настоящие аватарки, статусы проверок, связь коммита с PR.

Ложится на род «внешние данные» из фазы 2 без новых механизмов: кэш, TTL, дедупликация и запрет блокировать отрисовку уже есть. Добавляются аутентификация, хранение токена и разбор ответов конкретного API.

**Готовность:** аватарки подгружаются в фоне и переживают перезапуск; отсутствие сети или токена не мешает работать с репозиторием.

---

### Фаза 6. Операционный слой

Машинерия без единой видимой операции — сознательно.

`gitspy-exec`: запуск процессов, `GIT_ASKPASS` и свой бинарь-помощник, `GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS`, заглушка редактора и пейджера. Очередь по одной операции на репозиторий. Отмена на сетевой фазе. Нормализация ошибок. Наблюдатель за файловой системой в единую точку инвалидации из фазы 2.

**Готовность:** тестовая операция проходит весь путь, включая запрос учётных данных через диалог; отмена не оставляет `index.lock`; вторая операция встаёт в очередь, а не падает.

**Почему отдельной фазой:** это то, что невозможно прикрутить потом. Наивно запущенный git виснет навсегда, ожидая ввода с несуществующего терминала.

---

### Фаза 7. Операции записи

stage/unstage, commit, checkout, ветки, fetch/pull/push, merge. Каждая проверяется дифференциально: выполнили через нас, выполнили через git CLI, сравнили состояние репозитория.

---

## 5. Чего нет в ближайших двух фазах

Операций записи, diff, интеграций, свёртки цепочек. Причина одна: пока данные неверны на большом репозитории и весь репозиторий едет в память при открытии, любая фича сверху наследует обе проблемы.

---

## 6. Требует решения до кода

**Свёртка цепочек.** Делалась дважды и оба раза неверно. Первая версия сворачивала подряд идущие коммиты любого автора — включая обычные, чего никто не просил. Вторая давала выбрать автора, но правило всё равно неудачное: бот-цепочки от `argocd-image-updater` идут вперемешку с человеческими и под правило «подряд от одного автора» целиком не попадают.

Прежде чем писать код в третий раз, надо решить, **что именно должно сворачиваться**. Кандидаты в признак: совпадающий префикс сообщения, отсутствие изменений в исходниках, явная метка бота, отсутствие связи с PR. Это продуктовый вопрос, а не технический, и он не привязан к фазе.

---

## 7. Предлагаемые изменения спеки

1. **Раздел 5, дисковый кэш раскладки — убрать.** Замер: топология 18.7 мс на 35 тысяч коммитов, экстраполяция на миллион — порядка полусекунды. Репозиторий уже целиком на диске, база объектов git и есть кэш. Свой файл дублирует данные ради экономии, которой нет, и заводит класс тихих багов с устаревшей инвалидацией. Заменить разделом 3 этого документа — слоем данных, где кэш на диске отведён внешним источникам, у которых локального источника нет.
2. **Раздел 5, `commit-graph`** — понизить в значимости: замер показал 10% выигрыша, потому что упираемся не в топологию.
3. **Раздел 12, порядок работ** — заменить фазами из этого документа. Реальный ход оказался вертикальным срезом, и это было правильно: он выявил дефект порядка обхода и настоящее распределение времени, чего восемь последовательных этапов не показали бы.

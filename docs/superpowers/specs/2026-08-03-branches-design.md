# Ветки: кто владеет состоянием репозитория

**Дата:** 2026-08-03
**Основание:** разбор журналов GitKraken на машине заказчика (52 файла),
замеры на `~/projects/react` (35 074 коммита, 1 118 ссылок), перепись
существующих путей к git в коде.

Задача пришла продуктовой: ветки деревом, переход двойным щелчком, создание
локальной из удалённой, стрелки «впереди / позади». По дороге выяснилось, что
она архитектурная — у нас несколько путей к одному репозиторию, и наивное
решение добавило бы ещё один.

---

## 1. Сколько путей к git у нас есть

Перепись по коду, а не по памяти:

| № | Путь | Что берёт |
|---|---|---|
| 1 | **gix** (`gitspy-repo`) | обход истории, метаданные коммитов, ссылки, HEAD, worktrees |
| 2 | **системный git** (`gitspy-exec`) | все записи; чтения: `status --porcelain=v2`, `show --name-status`, `show ref:path`, `rev-parse` |
| 3 | **голая файловая система** (`gitspy-exec`) | `MERGE_HEAD`, `REBASE_HEAD`, `CHERRY_PICK_HEAD` через `std::fs::read_to_string` |
| 4 | **HTTP к хосту** (`gitspy-hosts`) | pull requests, аватарки |

Первая редакция этой спеки добавляла пятый — `for-each-ref` ради стрелок — и
тем заводила **второй источник для двух фактов сразу**: ссылки уже читает gix,
`ahead`/`behind` для текущей ветки уже отдаёт `git status`.

Проблема не в числе механизмов. Проблема в числе источников одного факта. Один
такой у нас уже есть и работает: **текущая ветка** приходит и из gix
(`head_ref` → `is_head`), и из `git status --branch` (`tree.branch`). Топбар
показывает первое, панель рабочего дерева — второе. Разойтись они могут, и
заметить это будет нечем.

---

## 2. Решение: git владеет состоянием, gix владеет объектами

> **gix отвечает за объекты навалом** — обход истории и метаданные коммитов.
> Это единственная работа, где библиотека выигрывает у процесса.
>
> **Системный git отвечает за состояние репозитория** — какие есть ссылки, куда
> указывают, какая текущая, кто кого отслеживает, насколько разошлись, что в
> рабочем дереве.

Работы двух механизмов после этого не пересекаются: спорить им не о чем.

### Почему именно так — три варианта и их цена

**А (принят): git владеет состоянием.**

| | сейчас через gix | через `for-each-ref` |
|---|---|---|
| 1 117 ссылок react | 13.2 мс | **18.8 мс** |
| 73 ссылки quesk | — | **27.1 мс** |
| отдаёт | имя, вид, oid | то же плюс `%(HEAD)`, тип объекта, разыменованный тег, upstream, ahead/behind |

**Поправка к первой редакции этой спеки.** Там стояло «10 мс против 13.2, строго
быстрее». Это была правда про сам git и ложь про нас: голая команда правда
считает всё за 10–20 мс, но запуск процесса из приложения стоит ещё столько же.
Замер `dump_repo` виден насквозь: на react с 1 117 ссылками уходит 18.8 мс, а на
quesk с 73 — **27.1 мс**. Больше ссылок, меньше времени. Значит платим не за
ссылки, а за процесс, и это порядка двадцати миллисекунд независимо от размера
репозитория.

Решение от этого не меняется, но держится теперь на другом: не на скорости, а на
том, что один вызов отдаёт **строго больше** и уносит 64 строки нашего кода —
`branches_and_tags`, `classify`, `points_at_commit`, `checked_out_branch`,
`RefRecord` и сборку `is_head`. Две из них — ручные починки первой фазы (галка по
имени ссылки вместо oid; тег, указывающий на blob), и обе становятся полем
формата.

**Второй процесс за oid HEAD не запускается зря.** Если какая-то ссылка помечена
`%(HEAD)`, HEAD указывает на тот же объект, и спрашивать `rev-parse` незачем:
это экономит ещё около десяти миллисекунд везде, кроме отсоединённого HEAD.

**Б (отклонён): gix оставляет себе ссылки, у git спрашиваем только upstream и
счётчики.** Правок меньше, но два механизма продолжают читать `refs/` в разные
моменты, ручные починки остаются, а правило «имя у gix, upstream у git»
держится памятью разработчика. Правило, которое держится структурой, переживает
спешку; правило, которое держится памятью, — нет.

**В (отклонён): убрать gix совсем, всё через git.** Даёт один путь, но платит
там, где проект оптимизировали больше всего:

| | gix | через git |
|---|---|---|
| топология всей истории | 29 мс | 40 мс |
| **метаданные окна в 60 строк** | **0.13 мс** | **10 мс** |

Окно дёргается на каждой прокрутке. Убрать оттуда 10 мс можно только живым
процессом `git cat-file --batch`: управление процессом, разбор протокола,
перезапуск после падения, жизненный цикл на каждый открытый репозиторий, тупики
на трубах. **То есть В убирает зависимость, но добавляет код, а не убирает.**
gix бесплатно даёт индексы пакфайлов, разрешение дельт и `commit-graph`.

### Кто чем владеет после правки

| Факт | Источник |
|---|---|
| Какие есть ссылки, куда указывают, какого вида | `git for-each-ref` |
| Какая ссылка сейчас выбрана | `%(HEAD)` из того же вызова |
| upstream, ahead, behind, gone | тот же вызов |
| Записи стеша | `git stash list` |
| oid HEAD при отсоединённом HEAD | `git status --porcelain=v2 --branch`, уже вызывается |
| Порядок обхода, родители, метаданные коммитов | **gix** |
| Содержимое файла, изменённые файлы, статус, все записи | системный git |

**Цена, принятая осознанно.** Сейчас `open_repo` открывает репозиторий и без
установленного git — `Git::discover()` возвращает `Option`. После правки без
git не будет и списка веток. Мы делаем git-клиент: без git уже сейчас не
работают запись, статус, дифф и клон.

**Таблица слоёв в `CLAUDE.md` правится.** Она называет `gitspy-exec` «Запись», а
он читает статус с первой же фазы записи. Описание врало, а не код.

## 3. Ссылки читаются одним вызовом

```
git for-each-ref --format='%(HEAD)%09%(refname)%09%(objecttype)%09%(objectname)%09%(*objecttype)%09%(*objectname)%09%(upstream:short)%09%(upstream:track,nobracket)'
```

Правила разбора проверены на фикстуре с лёгким тегом, аннотированным тегом и
тегом на blob:

| ссылка | `objecttype` | `*objecttype` | что делаем |
|---|---|---|---|
| `refs/heads/main` | `commit` | пусто | берём `objectname` |
| `refs/tags/light` | `commit` | пусто | берём `objectname` |
| `refs/tags/heavy` | `tag` | `commit` | берём `*objectname` |
| `refs/tags/onblob` | `tag` | **`blob`** | **пропускаем** |

Правило одно: действующий oid — это `*objectname`, если он есть, иначе
`objectname`; ссылка берётся, только если действующий тип — `commit`. Тег на
blob, роняющий открытие репозитория (блокирующий дефект первой фазы), отсеивается
полем формата.

**`%(HEAD)`** даёт `*` ровно у одной ссылки. При отсоединённом HEAD — ни у одной,
проверено. Это то самое поведение, которое первая фаза чинила вручную.

**`%(upstream:track,nobracket)`** даёт `ahead 2, behind 1`, либо одну половину,
либо пусто при совпадении, либо `gone`. Проверено на фикстуре.

**Стеш идёт мимо.** `refs/stash` указывает только на `stash@{0}`, остальные
записи достижимы через её рефлог — потому их не видит и `for-each-ref`.
Источник — `git stash list --format='%H%x09%gd%x09%gs'`, он отдаёт все.

Живёт всё это в `crates/gitspy-exec/src/refs.rs`.

## 4. Откуда взяты продуктовые решения

Заказчик просил повторить поведение GitKraken. Вместо пересказа по памяти —
разбор его журналов в `~/.gitkraken/logs/repos/`: каждая операция с меткой
времени, началом и концом. Наблюдение снаружи, а не чтение чужого кода.

Два моих утверждения по памяти разбор опроверг. Поэтому здесь улики.

### Пула при переключении нет

**109 переключений, `Pull` следом за семью.** Задержки: 0.89, 1.66, 1.69, 2.55,
3.44, 4.75, 6.62 с — такой разброс даёт рука, а не таймер. `Pull` встречается
после чего угодно: после `Push`, после `Unstage`, после ничего.

Предположение заказчика описывало верный симптом — чужой коммит правда
появляется сам. Причина другая.

### Фоновый фетч, период — минута

Фоновый фетч **не пишет в журнал ни `started`, ни `finished`**, только провалы:
560 строк `fatal` против 38 `started`. Это и есть способ его измерить.

Промежутки между быстрыми отказами (`Could not resolve host`, без растягивающего
таймаута DNS): **минута — 20 раз из 67**, дальше 2, 8, 10, 17 минут по паре раз,
и 61–87 минут — это когда приложение было закрыто.

### Переход на удалённую ветку — это DWIM

Журнал пишет `Checkout refs/remotes/origin/X` и **не пишет** `Create ref
refs/heads/X`. Но локальная ветка после этого есть:

- после `Checkout refs/remotes/origin/master` идёт `Pull master`, а не
  `Pull origin/master` — пул работает по локальной;
- после `Checkout refs/remotes/origin/builds/facebook-fbsource` через четыре
  минуты идёт `Checkout refs/heads/builds/facebook-fbsource` — локальная уже есть.

Значит журнал называет **то, на что нажал человек**, а делается DWIM: локальная
ветка того же короткого имени создаётся с отслеживанием удалённой, а если уже
есть — просто переход.

Это опровергло первую редакцию, где стояло безусловное
`checkout -b X --track origin/X`: на существующей локальной ветке оно падает.

### Автостеш принадлежит пулу, не переключению

`Auto-stash uncommitted changes` встречается 20 раз и всегда в одной обёртке:
`Fetch` → `Merge origin/X into X` → `Auto-stash` → `Pop most recent stash`.
Вокруг `Checkout` его нет ни разу. Переключение при грязном дереве у GitKraken
просто не удаётся, и он показывает тост.

**Решение заказчика:** делаем так же. Молча стешить нельзя — работа уезжает
туда, где её потом ищут.

## 5. Дерево ссылок

Имя ветки режется по `/`. `pr/36451` → папка `pr`, лист `36451`. У удалённых
первый сегмент — имя remote, оно уже часть имени.

Правила сняты со скриншотов:

- **цепочки не схлопываются**: `fixtures › packaging › brunch › dev ›
  minimatch-3.1.5` — пять строк с нарастающим отступом;
- **папки и листья в общем алфавитном порядке**, папки наверх не всплывают:
  `ci` (папка), `develop` (лист), `feat` (папка);
- фильтр раскрывает ветви с совпадением и сравнивает с полным именем.

Чистая часть — `src/refTree.ts`: плоский список → дерево, без единого обращения
к React, под тестами.

## 6. Строка ветки

```
[✓]   ⌐ 36451                                    70↑
 ▲     ▲                                          ▲
текущая  отступ по глубине          впереди / позади, потолок 99+
```

- **Текущая** — галка слева и подложка строки. Признак из `%(HEAD)`, то есть по
  имени ссылки: две ветки на одном коммите не получат галку обе.
- **Стрелки** справа: `70↑`, `1↓`, при расхождении обе. Больше 99 — `99+`.
- **Без upstream — пусто, а не нули.** Ноль значит «сверено и совпало».
- **`gone`** — своя пометка: ветка отслеживает то, чего на сервере уже нет.
- **Наведение** даёт `⋮` справа.
- **Подсказка с полным именем** — `Tooltip` из shadcn, а не атрибут `title`.
  Сейчас в сайдбаре нативный: появляется через секунду, не там, где нужно, и не
  поддаётся оформлению. Имена веток длинные и обрезаются почти всегда, так что
  подсказка здесь — основной способ прочитать имя целиком.

## 7. Взаимодействие

| Жест | Что происходит |
|---|---|
| Одинарный щелчок | Ветка выделяется, граф едет на её коммит |
| Двойной по локальной | `git checkout <ветка>` |
| Двойной по удалённой | DWIM, см. ниже |
| Двойной по папке | Свернуть или развернуть |

Задержка между одинарным и двойным не нужна: выделение мгновенно и безвредно,
оно просто случается первым.

### Двойной щелчок по удалённой ветке

Решение принимается в Rust по уже прочитанным ссылкам:

- локальная с коротким именем **есть** → `git checkout <короткое имя>`;
- **нет** → `git checkout -b <короткое имя> --track <remote>/<короткое имя>`.

Короткое имя получается снятием префикса remote из списка remotes, а не
отрезанием до первого слэша: `origin/builds/facebook-fbsource` даёт
`builds/facebook-fbsource`.

Новая операция закрытого списка: `Operation::CheckoutTracking { upstream, local }`.

**Почему не `git switch <имя>` одной командой.** DWIM отказывается работать,
когда ветку с таким именем содержат два remote. Отказывается правильно, но нам
это состояние известно заранее из уже прочитанных ссылок — решив его у себя, мы
даём внятное сообщение вместо отказа git и не зависим от `checkout.defaultRemote`
в чужом конфиге.

### Отказ при грязном дереве

Тост с кодом ошибки. Ни автостеша, ни `--force`. Стеш рядом кнопкой, он уже есть.

## 8. Свежесть

`git fetch --all` в фоне, **по умолчанию раз в минуту** — как измерено у
GitKraken, — в настройках, с возможностью выключить.

Дальше работает построенное: фетч двигает `refs/remotes/**`, наблюдатель шлёт
`repo:changed`, `App` перечитывает репозиторий, чужой коммит появляется в графе,
стрелка меняет число. Новой цепочки не заводится.

Два правила, без которых фоновая задача вредит:

- **Полоса занята — фетч пропускается.** Очередь держит одну полосу на
  репозиторий; иначе фоновая задача встанет поперёк push, начатого человеком.
- **Операция человека отменяет идущий автофетч.** В журналах заказчика есть
  таймаут DNS длиной 1 072 056 мс — почти восемнадцать минут. Без отмены
  приложение на эти восемнадцать минут стало бы неотзывчивым, и виноват был бы
  не сетевой сбой, а мы.

### Что автофетч ломает по дороге

`what_changed` в `src-tauri/src/watcher/mod.rs` считает изменением всё под
`.git`, кроме `*.lock` и `objects/tmp_`. Но `git fetch` пишет `FETCH_HEAD`
**при каждом запуске**, даже когда ничего не приехало.

Без правки приложение перечитывало бы всю историю раз в минуту впустую: на react
это 36 мс чтения плюс полностью перезаполненный фронтенд, шестьдесят раз в час.

`FETCH_HEAD` и `.git/logs/` становятся шумом наравне с `*.lock`.

## 9. Чем проверяется

**Ссылки — фикстурами настоящего git**, как весь слой чтения. Набор фикстур
задаётся тем, что мы теперь разбираем сами: лёгкий тег, аннотированный тег, тег
на blob, тег на дерево, две ветки на одном коммите, отсоединённый HEAD, ветка
впереди, позади, разошедшаяся, без upstream, с исчезнувшим upstream, ветка с
одинаковым именем в двух remote, несколько записей стеша, пустой репозиторий.

Числа стрелок сверяются с `git rev-list --left-right --count`, то есть с
ответом git, независимым от `for-each-ref`.

**Существующие тесты `gitspy-repo` на ссылки не выбрасываются, а
перенаправляются** на новый источник: они сверяют наш разбор с `git for-each-ref`
и должны продолжать проходить. Тест, который зеленеет и до правки, и после,
ничего не сторожит — поэтому сначала переносится тест, потом удаляется gix-код.

**Дерево** — тестами `src/refTree.ts` без React.

**Аргументы операций** — рядом с существующими в `operations.rs`: существующая
локальная ветка не получает `-b`, отсутствующая получает `--track`, ни один путь
не содержит `--force`.

**Шум наблюдателя** — тест, что `FETCH_HEAD` не считается изменением, а
`refs/remotes/origin/main` считается.

## 10. Чего не делаем

**Глазик — фильтр графа по одной ветке.** Есть на скриншотах заказчика, решение
принято: не сейчас. Это правка чтения и раскладки, а не сайдбара.

**Содержимое меню `⋮`.** Кнопка рисуется, наполнение — отдельной работой.

**Пул при переключении.** GitKraken этого не делает, и делать это опасно: merge
или rebase запускались бы двойным щелчком.

**Третий путь — голое чтение `.git` файлов** (`MERGE_HEAD` и прочие) остаётся как
есть. Он неправилен по тому же правилу, но трогать его в этой работе незачем:
записано, чтобы не потерялось.

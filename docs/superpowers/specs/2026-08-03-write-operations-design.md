# Операции записи: вложенный git, fetch, pull, push

Дата: 2026-08-03. Первая настоящая запись в репозиторий. До сих пор список
операций держал две безопасные — `commit-graph write --reachable` и
`fetch --dry-run`, — и это была проверка формы, а не функциональность.

## 1. Зачем сейчас

Панель действий нарисована, но живёт в ней одна кнопка. Всё остальное —
подсказка «появится вместе со слоем операций». Слой стоит с пятой фазы:
очередь по одной операции на репозиторий, канал прогресса, обезвреженное
окружение, единая инвалидация по наблюдателю за `.git`. Не хватает самих
операций.

## 2. Git внутри приложения

**Требование:** приложение работает на машине без установленного git.

Сегодня `Git::discover()` ищет `git` в `PATH`. Без него отваливается не только
запись: строка рабочего дерева, дифф, стейдж и коммит тоже идут через
системный git. Граф при этом откроется — его читает `gix` своим кодом, — и это
худший вид поломки: приложение выглядит рабочим и молча не умеет половину.

**Решение** записано ещё в спеке переписывания и здесь исполняется: кладём git
в ресурсы приложения. Берём переносимые сборки `dugite-native` — те же, что у
GitHub Desktop, — по одной на платформу.

Порядок поиска: вложенный бинарь, затем системный. На машине разработчика
ничего не меняется, на машине без git всё работает.

Что это **не** ломает: вложенный git читает тот же `~/.gitconfig`, зовёт тот же
настроенный `credential.helper`, выполняет те же хуки из `.git/hooks`.
Конфигурация живёт в системе, а не в бинаре.

Цена: несколько десятков мегабайт на платформу. Точная цифра меряется при
упаковке и записывается в план, а не обещается.

Обязанность: git распространяется под GPLv2. Вместе с бинарём поставляется
текст лицензии и ссылка на исходники ровно той сборки, которую мы вложили.

## 3. Какие операции добавляются

### Fetch

`git fetch --all --progress`. Флага `--prune` не навязываем: удаление
отслеживающих ссылок — решение пользователя, и у него есть `fetch.prune` в
конфиге. Наша задача — не решать за git то, что git уже умеет настраивать.

### Pull

`git pull --progress`, без флагов слияния. `pull.rebase` и `pull.ff` — это
конфигурация человека, и подставлять `--rebase` или `--no-rebase` от себя
значит тихо менять его поведение.

Конфликт при слиянии — не ошибка приложения, а состояние репозитория. git
вернёт ненулевой код, репозиторий останется в состоянии merge, и это уже видно:
узел рабочего дерева показывает `in_progress`. Разбор конфликта — своя фаза;
здесь мы обязаны честно сказать, что произошло, и не соврать, будто всё прошло.

### Push

Два пути, и разница между ними не косметическая:

| Состояние ветки | Команда |
|---|---|
| upstream есть | `git push --progress` |
| upstream нет | `git push --progress --set-upstream <remote> <branch>` |

Отсутствие upstream видно из `status --porcelain=v2 --branch`: строки
`# branch.upstream` просто нет. Когда remote один — берём его; когда несколько
— спрашиваем, а не угадываем.

**Форсированного push здесь нет.** `--force-with-lease` переписывает чужую
историю, и его место — за отдельным подтверждением с показом того, что именно
будет потеряно. Кнопка, которая иногда делает force, — это способ однажды
стереть чужую работу.

## 4. Учётные данные

Клонирование уже умеет: токен уходит в git через `credential.helper` и
переменную окружения, а не в `argv`, потому что командную строку видит любой
`ps`. Тот же способ распространяется на fetch, pull и push по https.

Токен подставляется только для адресов своего хоста. Для `ssh` ничего не
подставляется — там работает ключ пользователя и `BatchMode=yes`, чтобы вместо
зависания на вопросе получить внятный отказ.

## 5. Прогресс — общий разбор, а не три копии

`git clone --progress` пишет через возврат каретки, и это же делают fetch и
push. Разбор строк уже написан для клонирования; он не про клон, а про прогресс
git вообще. Модуль переименовывается в `progress`, к стадиям добавляется
`Writing` (её показывает push).

Три операции с тремя копиями разбора разойдутся — вопрос только когда.

## 6. Ошибки

Правило проекта: Rust отдаёт код и параметры, фразу собирает фронтенд. Сырой
`stderr` идёт в `detail` как техническая подробность.

Поверх этого — узнавание двух самых частых отказов, потому что «git failed» не
говорит человеку ничего:

| Что случилось | Код | По какому признаку |
|---|---|---|
| push отклонён, не fast-forward | `exec.rejected` | `! [rejected]` и `non-fast-forward` |
| слияние оставило конфликты | `exec.conflict` | `CONFLICT (` или `Automatic merge failed` |

Узнавание — чистая функция над текстом, проверяется настоящими строками git.
Больше двух случаев не берём: чем длиннее список догадок по stderr, тем чаще
он врёт.

## 7. Готовность

- Приложение на машине без git выполняет операцию, а не сообщает `exec.gitNotFound`.
- Fetch по приватному репозиторию проходит с сохранённым токеном и не ждёт ввода.
- Push в ветку без upstream ставит upstream и не требует терминала.
- Отклонённый push показывает «не fast-forward», а не «git failed».
- Pull с конфликтом оставляет репозиторий в состоянии merge, и это видно в графе.
- Прогресс идёт живьём: полоса не стоит и не прыгает назад.

# gitspy: переписывание с нуля

**Дата:** 2026-08-01
**Статус:** согласовано, готово к составлению плана реализации

---

## 1. Зачем

Существующий gitspy (Electron + React + `simple-git`, ~19 700 строк) переписывается с нуля. Причина не в отдельных багах, а в отсутствии архитектуры: слоёв нет, направление зависимостей вывернуто, состояние размазано по глобальной шине событий, а граф и виртуализация построены на подходе, который не масштабируется.

### Что именно сломано в существующем коде

Зафиксировано как перечень проблем, которые новая архитектура обязана исключить **по построению**, а не дисциплиной.

**Слои.** `App.tsx` (858 строк) одновременно роутер, менеджер вкладок, префетчер аватарок, шина ошибок, хост уведомлений и менеджер watcher'ов. Разбиение на `atoms/molecules/organisms` формальное: `organisms/GraphViewport.tsx` — 734 строки.

**Направление зависимостей.** `electron/git/loadCommits.ts` импортирует типы из `src/components/commits/types/git.ts` — бэкенд зависит от внутренностей UI-компонента. Общего доменного слоя нет.

**Общение компонентов.** 25 разных нетипизированных `CustomEvent` на `window` (`ui:snack`, `graph:scrollbar-change`, `ui:navigate:lock`, `sidebar:auto-collapse` и далее). Плюс `window.currentRepoPath` как глобальная переменная. Плюс императивные мутации DOM мимо React: `document.querySelector('tr.commit[...]').classList.add('commit-active')`.

**Контракт IPC написан руками трижды** — в `electron/git/ipc.ts`, в `electron/preload.ts` (504 строки) и в `src/types/preload.d.ts` (360 строк). Три источника правды, расходящиеся при первом изменении.

**Git-слой.** 45 файлов вида `createXxxHandler()`, `getGit()` создаёт новый инстанс `simple-git` на каждый вызов. Ошибки глотаются: при падении `git log` `loadCommits` возвращает пустой результат, и UI показывает «репозиторий пуст» вместо ошибки. Парсинг вывода, аннотация stash и маппинг refs свалены в один файл на 270 строк.

**Граф.**
- Раскладка считается **дважды на каждое изменение массива коммитов**: `useGlobalGraphLayout` создаёт off-screen SVG и прогоняет весь движок ради номеров дорожек, затем `GraphViewport` создаёт второй движок и рендерит.
- `GraphEngine` мутирует DOM напрямую через `createElementNS` — не чистая функция, не тестируется, не переиспользуется.
- Виртуализируются только узлы. `branches[i].draw()` рисует линии **по всей истории всегда**, независимо от видимого окна.
- Горизонтальный скролл идёт через `CustomEvent` → `useState` → ре-рендер всего вьюпорта на каждый пиксель.

**Виртуализация.** Три независимых подписчика на один скролл-контейнер, каждый со своим состоянием. Подгрузка = `maxCommits += 2000` и полный перезапрос окна с `setCommits(новый массив)` → полный пересчёт графа. Расширение окна вверх работает на эвристике `userIntentUpRef` из `wheel`-события. `react-virtuoso` в зависимостях, но не используется.

**Блокирующая загрузка не на том.** `IndexingOverlay` блокирует открытие репозитория на сетевом запросе аватарок в GitHub API, а `hideBody` прячет таблицу до `avatarReady`. То есть приложение ждёт сеть ради косметики, показывая при этом недосчитанную геометрию.

**Тестов нет вообще**, `vitest` не подключён.

## 2. Принятые решения

| Решение | Выбор |
|---|---|
| Подход | Переписывание с нуля |
| Рантайм | Tauri + React + TypeScript |
| Чтение git | `gix` (gitoxide) в процессе |
| Запись git | Системный `git`, поставляемый вместе с приложением |
| Первая веха | Только просмотр истории |
| Визуальный стиль | GitKraken как база, плюс наши добавления |

### Про границы первой вехи

Первая веха — это **порядок работ, а не границы продукта**. Push, pull, fetch, commit, merge, rebase, stash обязательны для git-клиента и будут реализованы. Требование к архитектуре: расширение на операции записи не должно потребовать её переделки. Поэтому операционный слой (раздел 6) проектируется сейчас, наполняется позже.

### Про git-движок

Проверено по первоисточникам ([`crate-status.md`](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md), [lib.rs/gix-commitgraph](https://lib.rs/crates/gix-commitgraph)):

**Чтение в gix покрыто полностью** — отмечено сделанным: revwalk/traversal, status, tree diff, refs (транзакции и loose refs), index чтение и запись V2/V3, credentials. Весь путь первой вехи ложится на реализованное.

**Не реализовано и помечено как планируемое:** `push`, `send-pack / receive-pack client plumbing`, `drive a rebase operation`, `checkout, switch, restore and reset orchestration`, создание подписанных коммитов, запись commit-graph.

**Не реализована генерация текстового патча** (`[ ] text`, `[ ] binary`). Это и не нужно: дифф считает не gix и не мы. Список изменённого и переименования даёт `git show --name-status --numstat --find-renames`, содержимое файла на ревизии — `git show <ref>:<path>`, сравнение и отрисовку — Monaco `DiffEditor`. Мы делаем клиент git, а не свой git; собственный алгоритм диффа означал бы собственные пороги переименований и собственную эвристику двоичных файлов, то есть тихое расхождение с терминалом.

Поэтому запись идёт через настоящий `git`. Ставка на чужой roadmap в обязательной функциональности отвергнута.

### Про поставку git вместе с приложением

Требование: приложение должно работать на машине без установленного git. GitKraken исторически решал это встроенным libgit2 через NodeGit, но [объявил переход на git-исполняемый файл как единственный способ выполнения операций](https://www.gitkraken.com/blog/gitkraken-client-migrating-from-libgit2-to-git-executable). Повторять путь, из которого выбирается его первопроходец, не будем.

Кладём git внутрь приложения (как делает GitHub Desktop). Это даёт:

- работу на машине без git;
- настоящий git, а не частичную реимплементацию: hooks, LFS, rebase, всё остальное;
- сохранение пользовательской конфигурации — положенный рядом git так же читает `~/.gitconfig`, так же вызывает настроенный `credential.helper`, так же выполняет хуки из `.git/hooks`, потому что конфигурация живёт в системе, а не в бинаре;
- детерминированную версию git.

Цена — размер дистрибутива, порядка нескольких десятков мегабайт на платформу; **точную цифру нужно измерить** при упаковке. Даже с ним приложение остаётся кратно меньше нынешнего Electron-варианта.

В первой вехе бандл не требуется: чтение идёт через gix. Он появляется вместе с первой операцией записи.

## 3. Слои и направление зависимостей

**Правило:** зависимости идут строго в одну сторону, ни один слой не знает о том, что находится над ним.

### Rust

**`gitspy-core`** — чистая логика, ноль ввода-вывода, ноль Tauri. Доменные типы (`Oid`, `Commit`, `RefName`, `Lane`, `Row`), алгоритм раскладки дорожек, ортогональная маршрутизация рёбер, назначение цветов, свёртка цепочек. Чистые функции над данными, тестируются на синтетических топологиях без диска и UI.

**`gitspy-repo`** — работа с репозиторием на диске: открытие через `gix`, revwalk, чтение refs, кэш раскладки и его инвалидация. Зависит от `core`.

**`gitspy-exec`** — запуск системного `git` для операций записи. Отвечает в том числе на вопрос «где лежит бинарь git» (системный или поставляемый с приложением); ничто выше него об этом не знает. В первой вехе почти пуст.

**`gitspy-app`** — команды Tauri. Тонкий слой: принял запрос, позвал нижние, вернул DTO. Логики нет. Появление логики в нём — признак, что она не на своём месте.

### Контракт Rust ↔ TypeScript

Типы DTO **генерируются из Rust**, TypeScript получается автоматически. Один источник правды вместо трёх. Рассинхрон становится ошибкой сборки, а не багом в рантайме.

### Renderer

- **`ipc/`** — единственное место во фронтенде, где встречается `invoke`. Наружу торчат типизированные функции.
- **`domain/`** — сгенерированные типы и работа с ними, без знания о React.
- **`features/history/`** — граф, таблица, виртуализация, мини-карта.
- **`ui/`** — примитивы без знания о домене.

Atomic Design не переносится: группировка по фиче отражает, что меняется вместе.

## 4. Граф

### Конвейер

```
gix revwalk (Rust)  →  раскладка дорожек (Rust, потоково)  →  кэш полос
                                                                  │
                              видимое окно (плоские массивы)  ←───┘
                                                                  │
                                                  Canvas-рендер (renderer)
```

### Раскладка

Однопроходный алгоритм: держим массив активных дорожек, для каждого коммита ищем дорожку, где он ожидается как родитель, иначе выделяем новую. Стоимость O(коммитов × активных дорожек); активных дорожек в реальных репозиториях десятки.

Считается в Rust потоково по мере revwalk, а не после переноса истории в JS.

### Полосы и снапшоты

Раскладка считается полосами (порядка 10 000 коммитов). В конце каждой полосы сохраняется **снапшот состояния активных дорожек**.

Это ключевая деталь: чтобы отрисовать полосу в середине истории, нужно знать, какие дорожки были активны на её границе. Со снапшотами прыжок в произвольное место требует досчёта одной полосы, а не всей истории сверху. Без них выбор был бы между «считать всё сразу» и «врать в раскладке».

### Правила раскладки (согласованы по скриншотам GitKraken)

- **Колонки раздаются жадно слева** по мере появления линий при обходе сверху вниз. Текущая ветка **не** привилегирована и не прибита к нулевой колонке — на референсных скриншотах `master` находится во второй колонке.
- **Цвет определяется номером колонки.** Колонка 0 всегда одного цвета на всю историю, колонка 1 — своего, и так далее.

  Это исправление первоначального решения. Сперва здесь было записано «цвет закреплён за линией» — вывод из рассматривания скриншотов, не подтверждённый проверкой. На практике он даёт вот что: линия в колонке умирает, слившись с соседней, её место занимает следующая и получает новый цвет — магистраль меняет цвет посреди истории без всякой причины. На репозитории `quesk` нулевая дорожка так распадалась на 115 голубых коммитов и 301 розовый.

  Плата за привязку к колонке: две ветки, побывавшие в одной колонке в разное время, неотличимы по цвету. Это приемлемо ровно потому, что колонки стабильны — чем и занимается правило приземления ниже.

- **Приземление влитой ветки остаётся в её колонке.** Когда коммита ждут несколько дорожек, он достаётся не самой левой, а той, что открыта под второго родителя мержа. Иначе влитая ветка сдёргивается на магистраль, и линии зигзагом ходят влево-вправо вместо вертикалей.

  Признак «боковая» относится к конкретному ожиданию, а не к линии целиком: он снимается, как только линия идёт дальше по первому родителю. Если его наследовать, перескакивать между колонками начинает уже сама магистраль.
- **Рёбра ортогональные**: вертикаль → скруглённый угол → горизонталь. Не S-образные безье. Это и есть главное визуальное отличие от текущей реализации, и одновременно более дешёвая форма: сегмент описывается парой целых вместо четырёх контрольных точек, отсечение по видимому окну тривиально, на canvas ложится в `lineTo` + `arcTo`.
- **Шаг между колонками** превышает диаметр узла примерно на четверть.
- **Подсветка строки** цветом её дорожки, с ярким колпачком у правой границы колонки графа.
- **Локальный и удалённый ref показываются отдельно**, каждый на своём коммите — так видно отставание локальной ветки без счётчика ahead/behind. Текущая ветка помечается.
- **Тело коммита показывается инлайн приглушённым** после заголовка.

> **Палитра.** Значения цветов принадлежат renderer'у; `gitspy-core` оперирует индексами. В старом приложении была вручную подобранная палитра из 17 оттенков, разложенных по кругу (sky → blue → violet → pink → red → yellow → green → aqua). Старый код удалён, но палитра достаётся из истории:
> `git show b5122ab:src/components/graph/lib/graph.ts`
> Брать её как отправную точку на этапе 6, а не изобретать заново. Размер палитры и константа `PALETTE_LEN` в core обязаны совпадать — решается там же, на этапе 6.

### Рендер

Граф рисуется на **Canvas 2D**, строки таблицы остаются DOM (текст должен выделяться и быть доступным). Граф текста не содержит: узлы, линии, аватарки.

Canvas даёт один элемент вместо десятков тысяч узлов, перерисовку видимого окна за проход, и превращает горизонтальный скролл и попадание курсором в арифметику вместо запросов к DOM.

Аватарки рисуются через `drawImage` из общего кэша `ImageBitmap`.

### Добавления сверх GitKraken

**Сворачивание цепочек одного автора.** Фолдинг, а не фильтр: коммиты остаются на месте, не исчезают из счёта, раскрываются по клику. Правило задаёт пользователь явно (например «сворачивать подряд идущие коммиты от `argocd-image-updater`»), по умолчанию выключено. Угадывание по похожести сообщений не делается — это эвристика, которая однажды тихо спрячет важное.

**Подсветка родословной.** При выборе коммита его предки остаются яркими, остальное гаснет. Родители лежат индексами в массиве, поэтому это обход по видимому окну.

**Мини-карта всей истории** вдоль скроллбара: где какие ветки жили, где текущая позиция, клик — прыжок. Возможна потому, что раскладка всей истории посчитана заранее.

**Переключаемая плотность** строк — паритет с GitKraken, не отличие. Стоит ноль, поскольку высота строки и так параметр раскладки.

## 5. Загрузка, кэш и скролл

### Подгрузки при скролле не существует

Вместо «догрузить в конец» — **случайный доступ к окну поверх заранее известной топологии**.

**Топологический проход** при открытии: `gix` делает revwalk, беря только oid и родителей, без декодирования автора, даты и сообщения. На выходе — точное общее число коммитов, порядок и раскладка со снапшотами. Отсюда следует, что **скроллбар честный с первой секунды**: высота известна, можно швырнуть ползунок в конец истории и попасть туда.

**Метаданные по требованию окна**: renderer запрашивает диапазон строк, Rust декодирует ровно их. Скролл — смена диапазона; вверх, вниз и прыжок в середину суть одна операция. Вокруг видимого окна LRU-кэш на несколько тысяч строк.

### Один переход, готовый интерфейс

Полуготовый интерфейс, который меняется под руками (растущий скроллбар, едущие строки), хуже честного ожидания. Стриминг полос в живой UI отвергнут.

Правило: **блокируем на том, что меняет геометрию; не блокируем на том, что меняет только пиксели.** Топология и раскладка определяют положение всего — без них рисовать нечего. Аватарка не меняет ни одной координаты — она дорисовывается на месте. Ни `IndexingOverlay`, ни `hideBody` не воспроизводятся.

### Кэш раскладки

**Кэшируется** результат топологического прохода: упорядоченный массив oid, индексы родителей, дорожка и цвет на коммит, снапшоты полос.

**Не кэшируются** метаданные коммитов — автор, дата и сообщение уже лежат в базе объектов git, дублировать её значит удвоить размер репозитория на диске ради того, что декодируется за миллисекунды на окно.

**Формат** — бинарный, записи фиксированной ширины (родители как `u32`-индексы, дорожка `u16`, цвет `u8`), читается через `mmap`. Открытие кэша не требует парсинга, поэтому повторное открытие мгновенно независимо от размера истории. Лежит в app data по хешу пути репозитория; в чужой `.git` не пишем. В заголовке версия формата — смена алгоритма раскладки автоматически инвалидирует старые кэши.

**Ключ валидности** — снимок refs (`ref → oid`) на момент расчёта.

| Состояние refs | Действие |
|---|---|
| Совпали | Ничего не считаем |
| Продвинулись вперёд (старые вершины — предки новых) | revwalk от новых вершин с границей по старым; пересчёт полос от вершины до первой, чей снапшот совпал. Обычно одна полоса |
| Разошлись (rebase, amend, reset, force-push, удаление ветки) | Полный пересчёт |

Частичное перешивание кэша после rebase сознательно не делается: это класс багов, где граф тихо показывает несуществующие связи.

### commit-graph

`gix-commitgraph` умеет только чтение. Поэтому commit-graph — **необязательная оптимизация первого открытия**, а не требование:

- есть в репозитории → gix читает, первое открытие мгновенно;
- нет, но найден системный git → просим записать в фоне;
- нет и git не найден → не делаем ничего, gix распакует объекты сам.

Все последующие открытия закрывает собственный кэш раскладки, который от git не зависит.

## 6. Операционный слой

Проектируется сейчас, наполняется по мере добавления операций записи.

### Операция как объект первого класса

У сетевой git-операции есть идентификатор, поток прогресса, возможность отмены, и она может закончиться не только успехом или ошибкой, но и **требованием ввода**. В `Promise` это не оборачивается без потерь.

Операция — запущенный процесс с каналом событий: `progress`, `needs-input`, `done`, `failed`. Renderer подписывается по id.

### Интерактивность

Главная причина проектировать операции заранее. Наивно запущенный git виснет навсегда, ожидая ввода с несуществующего терминала.

- `GIT_TERMINAL_PROMPT=0` — git не пытается спрашивать через терминал, падает с внятной ошибкой;
- `GIT_ASKPASS` указывает на наш бинарь-помощник: git вызывает его со строкой запроса и ждёт ответ в stdout; помощник обращается к приложению, приложение показывает диалог, ответ уходит обратно;
- `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` — то же для passphrase от ключа;
- `GIT_EDITOR` заглушается, слияния идут с `--no-edit`;
- `GIT_PAGER=cat`.

### Сериализация

Одна операция записи на репозиторий за раз, очередь на стороне приложения. git сериализуется через `index.lock`, но грубо — вторая операция просто падает.

Отмена допустима только на сетевой фазе: прерывание записи объектов оставляет мусорный lock. Отменяемость — свойство конкретной операции, а не общее.

### Инвалидация

Любая запись меняет refs, индекс или рабочую копию. Путь один: операция завершилась → `gitspy-repo` перечитывает refs → сравнивает со снимком → инвалидирует затронутое.

Наблюдатель за файловой системой нужен, потому что пользователь может сделать коммит в терминале мимо приложения. Оба источника — операция и watcher — сходятся в одну точку инвалидации.

### Ошибки

Слой нормализации превращает известные случаи в типизированные: non-fast-forward, отказ аутентификации, конфликт слияния, грязная рабочая копия, detached HEAD, занятый lock — у каждого сказано, что делать дальше. Неопознанное отдаётся как есть, с полным stderr.

**Глотать ошибку и возвращать пустой результат запрещено.**

## 7. Состояние в renderer

### Три вида состояния

**Серверное** — то, что живёт в Rust и лишь отражается в UI. Это кэш ответов, а не состояние приложения. Делится надвое:

- *дискретные данные* (детали коммита, diff файла, список веток, статус) — обычный слой запросов (TanStack Query): кэш по ключу, инвалидация, отмена при смене выбора;
- *окно истории* — **отдельный `HistorySource`**, потому что ключ там непрерывный. Кэшируются диапазоны, с LRU и склейкой соседних. Попытка натянуть на это слой запросов даст либо тысячи ключей, либо перезапросы на каждый пиксель.

**Сессионное** — открытые вкладки, активный репозиторий, выбранный коммит, плотность, свёрнутые группы, ширины колонок. Стор (Zustand), нарезанный срезами по фичам. Активный репозиторий идёт вниз явно; `window.currentRepoPath` не воспроизводится.

**Эфемерное** — `scrollTop`, диапазон видимых строк, положение курсора, горизонтальный скролл графа. **В React не попадает вообще:**

- виртуализатор один на экран, владеет `scrollTop` в ref;
- диапазон публикует через подписку, не через `setState`;
- canvas читает диапазон напрямую и рисует в `requestAnimationFrame`, минуя React — при скролле не происходит ни одного React-рендера;
- таблица DOM обновляется только при смене набора строк.

Три независимых подписчика на один скролл-контейнер невозможны по построению: подписчик один, остальные читают у него.

### Общение компонентов

**Никаких `window`-событий.** Общий родитель или срез стора.

Проверка, которую нынешний код не проходит: открыв файл компонента, можно понять, откуда приходят данные и куда уходят действия, не грепая по проекту строку `'ui:snack'`.

### События из Rust

Один слой `ipc/events`, типизированный, переводящий события Rust в инвалидацию запросов и обновление стора. Компоненты на события Rust не подписываются никогда.

Это же единственная точка, куда приходит «репозиторий изменился» — одинаково от операции и от watcher'а.

### Императивный DOM

Ноль. Активная строка — это данные, а не класс, навешиваемый руками мимо React.

Осознанное исключение — canvas: рисование в 60 кадров через VDOM бессмысленно. Он заперт внутри одного компонента с явным входом (диапазон, раскладка, тема) и снаружи выглядит обычным компонентом.

### Уведомления

Один срез стора и одна функция. Ошибки операций попадают туда из единственной точки — из обработчика результата операции.

## 8. Тестирование

### Раскладка графа

Топологии описываются текстом (`m3 <- m2, b1`), а не репозиториями — алгоритму нужны только хеши и родители.

**Property-based на инвариантах:** у каждого коммита ровно одна дорожка; две живые линии не занимают одну дорожку в одной половине строки; ребро соединяет коммит с настоящим родителем без разрывов; линии непрерывны между строками — ни одна не обрывается и не возникает из ниоткуда, кроме вершины; число ответвлений равно числу родителей минус один; цвет всех коммитов одной дорожки совпадает.

**Главный инвариант:**

> раскладка всей истории целиком совпадает со склейкой раскладок по полосам, посчитанных от снапшотов.

На этом равенстве держится вся схема с полосами. Его нарушение не падает и не бросает исключение — граф просто начинает врать в раскладке при прыжке в середину истории. Глазами не проверяется, тестом проверяется тривиально.

**Golden-тесты в ASCII** — проверенные вручную истории сохраняются текстовой картинкой, diff читается человеком.

### Слой репозитория — дифференциально против настоящего git

Тестовые репозитории собираются скриптом через системный git с фиксированными датами и авторами, чтобы хеши были воспроизводимы. Сравнивается: порядок revwalk против `git log --date-order`, refs против `git for-each-ref`, статус против `git status --porcelain`, изменённые файлы против `git diff --name-status`.

### Кэш

Инвариант: **результат из холодного кэша совпадает с результатом из горячего** после любой последовательности операций. Property-based: случайные цепочки (коммит, ветка, merge, rebase, force-push, удаление ветки, gc), сравнение после каждого шага.

Здесь ловятся ошибки инвалидации, которые иначе всплывают через месяц как «граф показывает фигню, помогает перезапуск».

### Операции записи

Дифференциально: выполнили через нас, выполнили тот же сценарий через git CLI, сравнили итоговое состояние репозитория.

Отдельно: askpass вызывается вместо зависания; отмена на сетевой фазе не оставляет `index.lock`; вторая операция встаёт в очередь, а не падает.

### Renderer

Виртуализатор и `HistorySource` — чистая логика над числами и диапазонами, покрываются полностью.

**Canvas не тестируется попиксельно** — такие тесты ломаются от смены шрифта и сглаживания, и их начинают обновлять не глядя. Рендер разрезан надвое: чистая функция «раскладка + видимое окно → список примитивов» тестируется обычными сравнениями; тонкий слой, кладущий примитивы на canvas, не тестируется, в нём нет решений.

Компоненты — только там, где есть настоящая логика. Тесты вида «отрендерилось без падения» не пишутся.

### Производительность

Бенчмарк с порогом в CI: раскладка большой синтетической истории, досчёт полосы, ответ на запрос окна. Просадка — красная сборка. Иначе производительность, ради которой затевался Rust, утечёт незаметно.

## 10. Что проверить до начала работ

**Спайк на push в gix.** Есть расхождение: docs.rs показывает у высокоуровневого `gix` модуль `push`, тогда как `crate-status.md` содержит `[ ] push`. Предполагаю, что модуль относится к rev-spec `@{push}` («куда бы ты запушил»), а не к отправке. Для планирования принято осторожное «push не реализован»; проверить руками до того, как закладывать что-либо на этом.

**Измерить размер поставляемого git** по платформам, чтобы оценить итоговый размер дистрибутива.

**Замерить топологический проход gix** без commit-graph на репозитории порядка 10⁵–10⁶ коммитов, чтобы понять реальную длительность единственного экрана ожидания.

## 11. Целевые показатели

«Мгновенно» здесь означает **не более 100 мс до готового интерфейса** — без промежуточного экрана загрузки.

| Репозиторий | Первое открытие | Повторное | После pull | После rebase |
|---|---|---|---|---|
| Малый | мгновенно | мгновенно | мгновенно | мгновенно |
| ~100k коммитов | доли секунды | мгновенно | мгновенно | десятки мс |
| ~1M коммитов | секунды, с прогрессом | мгновенно | мгновенно | десятки мс |

Единственная клетка с заметным ожиданием — первое открытие очень большого репозитория без commit-graph, и оно случается один раз в жизни репозитория.

Скролл: ни одного React-рендера на кадр, перерисовка только видимого окна.

Числа в колонке «первое открытие» — ожидания, а не измерения; уточняются замером из раздела 10.

## 12. Порядок работ внутри первой вехи

Первая веха слишком велика для одного плана реализации, поэтому разбивается на этапы. Каждый заканчивается чем-то проверяемым; последующий опирается на предыдущий.

**Этап 1 — ядро раскладки.** `gitspy-core`: доменные типы, однопроходный алгоритм дорожек, назначение цветов, ортогональная маршрутизация. Текстовые фикстуры топологий, property-based тесты, golden-тесты в ASCII. Ни диска, ни Tauri, ни UI. Проверяемо целиком тестами.

**Этап 2 — чтение репозитория.** `gitspy-repo` на `gix`: открытие, топологический проход, refs, окно метаданных. Дифференциальные тесты против настоящего git. Всё ещё без UI.

**Этап 3 — кэш.** Бинарный формат, `mmap`, снимок refs, три сценария валидности. Property-based на совпадении холодного и горячего кэша. Инвариант «целиком == по полосам» из этапа 1 проверяется уже на реальных историях.

**Этап 4 — Tauri-слой и контракт.** `gitspy-app`, генерация типов, `ipc/` в renderer. Проверяемо тем, что окно истории доезжает до фронтенда типизированным.

**Этап 5 — виртуализация и таблица.** Единственный виртуализатор, `HistorySource` с LRU по диапазонам, DOM-таблица строк. Граф ещё не рисуется. Уже можно скроллить реальную историю с честным скроллбаром.

**Этап 6 — canvas-граф.** Чистая функция «раскладка + окно → примитивы», затем слой отрисовки. Аватарки, подсветка строк, бэйджи веток.

**Этап 7 — детали коммита и diff.** Список изменённого от `git show --name-status`, содержимое от `git show <ref>:<path>`, сравнение и отрисовка — Monaco.

**Этап 8 — добавления.** Подсветка родословной, мини-карта, сворачивание цепочек, переключаемая плотность.

Этапы 1–3 не требуют ни строчки фронтенда, и это сознательно: самая сложная и самая ломкая часть проекта закрывается тестами до того, как появится UI, в котором её ошибки станут невидимыми.
